DWARF — State-Lifecycle / Recovery Differential

"What happens across restart, crash-recovery, and cold-start?" · cardano-node vs Amaru · source analysis + live DWARF run · 2026-07-18
DWARF's oracles watch two nodes' chain tips. They don't test a node's own life events — restart, crash-recovery, cold-start after bootstrap. Result: cardano-node keeps a self-contained ledger state and replays from the newest snapshot (falling back to genesis) to self-heal on startup; Amaru splits state across four cross-consistent stores, needs three epochs of snapshot history to operate, and cannot rebuild from genesis. The durable difference is the recovery model. A live run corrected one predicted finding: a freshly bootstrapped Amaru crosses epoch boundaries cleanly on the normal bundle path (the bundle ships the 3 required snapshots) — no warmup crash. No exploit — a lifecycle model gap DWARF should test.

Live run — a freshly bootstrapped Amaru crosses epoch boundaries cleanly verified · on box

We fresh-bootstrapped a real Amaru node (amaru-relay-2): wiped its stores, restarted; its startup re-imported the trusted bundle — which ships exactly MIN_LEDGER_SNAPSHOTS = 3 snapshots (slots 124/246/366) — then forward-synced from ~epoch 2. It crossed epoch boundaries cleanly: 49+ consecutive transitions, 0 panics, 0 NoSuitableStakeDistribution, 0 roll-forward errors, restarts=0. The N-2 machinery is exercised (stake_distribution_epoch = current_epoch − 3, snapshot + prune each boundary) and succeeds because the bundle satisfies it. (Full replay-to-tip didn't finish — the post-reboot mesh was frozen and the upstream relay dropped chainsync; environmental, not a lifecycle defect.) This corrects the earlier predicted "valid block fails at first boundary" claim. Evidence: consensus-state-lifecycle-evidence/logs/live-run-2026-07-18.txt.

Why the dependency is real (the mechanism, when history is missing)

Crossing an epoch boundary reads state from two epochs ago. If a bootstrap does not supply that aligned history, the read fails: 
// crates/amaru-ledger/src/state.rs
pub const MIN_LEDGER_SNAPSHOTS: u64 = 3;

fn epoch_transition(next_epoch) {
    ... self.snapshots.for_epoch(next_epoch - 2)?        // N-2 snapshot
    ... self.stake_distribution(next_epoch - 2)?         // N-2 stake distribution
}

// StakeDistributionView::new -> if the deque lacks that epoch:
//   Err(StateError::NoSuitableStakeDistribution(epoch))
// -> forward(): Err => "Failed to roll forward the ledger state"  (a VALID block)
This is the failure mode only for a bootstrap that lacks the aligned N-2 snapshots — not the normal bundle path (see the live run above). The earlier false-leadership-campaign crash was under a non-standard forged setup, not a normal bootstrap. cardano-node has no equivalent constraint: its stake distribution is part of a self-contained ledger state reconstructed by replay.

Why it matters (no exploit — a model gap)

Splitting state into snapshot/stake stores and bootstrapping from a snapshot are legitimate designs. The finding is that the two nodes recover differently, and DWARF's convergence oracles can't see it. A lost/corrupt store that cardano-node would replay past (down to genesis) becomes, in Amaru, unrecoverable without a re-imported snapshot — and a store-invariant violation is a panic, not a recovery. The N-2 snapshot dependency is real but satisfied on the normal bootstrap path (verified live); it becomes a liveness edge only for an incomplete bootstrap — which a tip oracle would register only as "Amaru stopped advancing."

What DWARF should add

A lifecycle dimension to the differential harness: for each node drive restart mid-epoch, restart across an epoch boundary immediately after bootstrap, kill -9 mid-write then reopen, and (later) on-disk-format upgrade; assert the node returns on the same state and does not crash, and compare the two implementations. Amaru's warmup window and cardano-node's replay recovery are the first two behaviours to encode; the observed epoch-boundary crash is the seed case.
