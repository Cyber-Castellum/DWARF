DWARF — False-Leadership (Forged-VRF) Rejection Differential

Does each node enforce the VRF leadership threshold, or only that the proof verifies? · cardano-node 10.7.1 vs Amaru · cardano_amaru devnet (k=5, f=0.2, epoch 125) · generated 2026-07-17
We forged blocks with a valid VRF proof but an unearned win (leader value above the active-slot threshold) and served them to both implementations. Both reject them — cardano-node with VRFLeaderValueTooBig, Amaru with Insufficient leader stake. Differential: AGREE. Amaru enforces the leadership threshold — it is secure against any-stake block forgery.

The security question

A Praos block producer proves its right to a slot with a VRF output. Legitimacy needs two checks: (1) the VRF proof verifies, and (2) the resulting leader value is below a threshold set by the active-slot coefficient f and the producer's stake σ — i.e. the producer actually won the lottery. A node that checks only (1) would accept blocks from a producer that never won the slot: any-stake block forgery, a catastrophic break. This test asks whether Amaru enforces (2), and whether it agrees with cardano-node.

Method — a patched forger that mints unearned wins

We patched the ouroboros-consensus-cardano db-synthesizer (env gate DWARF_FALSE_LEADERSHIP=1) to raise the per-era active-slot coefficient (praosLeaderF/tpraosLeaderF) to ~0.99 inside the forger only — leaving praosRandomnessStabilisationWindow and the genesis untouched, so nonce evolution is unchanged and the forged chain still connects to the real genesis. The forger then "wins" ~every slot regardless of stake.

The nodes even agree block-by-block: they accept the few early slots the producer could legitimately have won and reject at the first block whose leader value genuinely exceeds the threshold. Neither adopts a single unearned block.

Behavioural note for the Amaru team robustness

Setting the test up surfaced an unrelated Amaru crash: when Amaru forward-syncs across an epoch boundary from a freshly bootstrapped snapshot, it panics on an internal assertion (amaru-ledger/src/state.rs:514: "unexpected stake distribution for epoch") rather than handling it. We worked around it by confining the forged blocks to a single epoch. This is a crash/availability bug, not a consensus-safety divergence — details and a repro sketch in finding-amaru-vrf-leadership-epoch-panic.md.
