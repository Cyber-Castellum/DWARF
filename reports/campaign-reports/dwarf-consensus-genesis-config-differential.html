DWARF — Genesis/Config-Acceptance Differential

Do cardano-node and Amaru agree on which genesis configs are valid? · cardano-node 10.7.1 vs Amaru · cardano_amaru testnet_42 · generated 2026-07-18
A new surface: the genesis both nodes ingest at startup (the "stored" input, vs the messages/blocks fuzzing already covers). Feed each the same mutated shelley-genesis.json and compare accept/reject. Result: one confirmed cardano-node crash, one well-supported architectural asymmetry in how Amaru validates genesis, and one preliminary leniency lead held back for cleaner evidence.

Severity & scope — read first

Nothing here is a critical or exploitable security finding. The value is the method (a config-acceptance differential — a surface DWARF didn't previously cover) and two honest observations.
  • Finding 1 is a low-severity robustness bug, not a vulnerability. The genesis is trusted operator-set config — an attacker can't feed a node a malicious genesis over the network, so there is no attack surface. The bug: cardano-node crashes instead of cleanly rejecting a malformed genesis. Belongs upstream as a cardano-node (IntersectMBO) robustness issue.
  • Finding 2 is the Amaru-relevant result — an architectural observation about how Amaru validates the genesis. No exploit; a design point.
  • Finding 3 is a preliminary lead, deliberately not claimed (flaky data).

Finding 1 — cardano-node crashes on unguarded time-parameter division confirmed · systematic

A sweep of 417 single-field genesis mutations (every numeric field × a 15-value edge palette), timing-classified — clean REJECT ~20 ms, CRASH ~140 ms, ACCEPT = not-rejected-in-3 s:
OutcomeCount
REJECT (clean, ~20 ms)339
ACCEPT (not rejected)75
CRASH (uncaught exception)3
All 3 crashes are a division reaching zero on a time parameter: 
epochLength = 0       -> divide by zero
slotLength  = 0       -> Ratio has zero denominator
slotLength  = 1e-300  -> Ratio has zero denominator   (underflows to 0)
Fast-failing, not a hang — but a crash instead of a clean rejection. Fix: range-check epochLength > 0 and slotLength > 0 at decode.

Also (hedged): genesis validation is largely type/parse-level, not semantic — the node accepts slotLength=-1 (while 0 crashes), zero maxKESEvolutions, and enormous securityParam/epochLength. Some may be intentionally unconstrained; the negative-vs-zero slotLength inconsistency is the concrete part.

Finding 2 — the two clients validate genesis in fundamentally different ways well-supported

Wherereads/validates raw shelley-genesis.json directly at node startupconsumes pre-derived AMARU_GLOBAL_* from a separate component (bootstrap-producer); does not re-validate the raw genesis at amaru run
Speed~20 ms clean rejectseconds–minutes; intermittently hangs
Determinismdeterministicnon-deterministic on bad input (activeSlotsCoeff=2.0 → 1/f=1 one run, 1/f=5 another)

Different config-trust models: cardano-node treats genesis as untrusted input to validate up front; Amaru trusts a derived-params artifact and never re-checks the source. A malformed/mis-derived genesis can propagate into Amaru silently.

Finding 3 — Amaru leniency preliminary — NOT a finding

Some mutations hint Amaru is more lenient (clearest: slotLength=0 — cardano-node crashes, Amaru accepts and boots on baseline params). But Amaru's derivations were non-deterministic and several runs hung, so the per-mutation verdicts are not reliable. Confirming this needs a deterministic Amaru genesis-parse surface (its own parser, or amaru import with a hard timeout). We deliberately do not claim "Amaru accepts invalid genesis" on this evidence — that would be the LEAD-001 mistake (a harness artifact dressed as a finding).
